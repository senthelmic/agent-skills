# Baseline: coding standards and conventions

What a good conventions section looks like. Mechanics are in
[../generators/coding-standards.md](../generators/coding-standards.md); this
file is opinion, and a team may replace it — see [README.md](README.md).

---

## The one test

**Could you name the lookup that would prove this rule true or false?**

If you cannot, it is filler. Leave it out.

"Write clean code" has no lookup. "Handlers in `src/api/` return `{ data }`" has
one: open two handlers. That difference is the whole quality bar for this
artefact.

---

## Four true rules beat thirty generic ones

This is the capability most likely to fail the *specific* criterion, and the
failure mode is always the same: a long list of things that are true of every
codebase in the world.

**A generic rule is not harmless.** It dilutes the specific rules around it,
teaching the agent that this section is boilerplate to skim. Two files of ten
lines each, one true and one padded to fifty, are not equally useful — the
padded one is worse than the short one.

Aim for **five to twelve rules**. If you have more, the extras usually belong in
a skill about the library they concern.

---

## Write the rule the code already follows

The conventions section records **what this repository does**, not what someone
wishes it did.

An aspirational rule is a trap. The agent follows it, produces code that matches
nothing else in the repository, and the reviewer rejects it — and the agent
looks unreliable when the file was at fault.

If the developer states an aspiration during the interview, write it, and mark
it plainly:

```markdown
- New handlers return `{ data }`. Older handlers in `src/api/legacy/` return
  bare objects and are not being changed.
```

Naming the exception is what makes the rule usable. A rule with an unnamed
exception will be contradicted by the first file the agent opens.

---

## Anchor every rule to a path

A rule with no location is a rule the agent cannot apply confidently.

| Weak | Strong |
|---|---|
| "Use `AppError` for errors." | "Errors cross the API boundary as `AppError`; do not throw raw `Error` in `src/api/`." |
| "Tests go beside the source." | "Tests sit beside the source as `<name>.test.ts`. `tests/e2e/` is the one exception." |
| "Don't edit generated files." | "`src/db/schema.ts` is generated by `pnpm db:generate` — never hand-edit it." |

---

## What is worth a rule

Ranked by how often an agent gets it wrong without being told:

1. **What is generated and must not be hand-edited.** The most damaging thing to
   get wrong, and invisible from the file itself.
2. **The shape of an API response or a returned error.** Wrong here means wrong
   everywhere, silently.
3. **Where a new file of a given kind goes.** An agent that guesses will guess
   plausibly and wrongly.
4. **Test layout and naming.** Cheap to state, constantly needed.
5. **Import style** — aliased or relative. Small, but it shows up in every file.

---

## Reject, always

- "Write clean, maintainable code."
- "Follow best practices."
- "Use meaningful variable names."
- "Keep functions small."
- "Add comments where the code is complex."
- Anything a linter already enforces. The linter runs; the sentence does not.

That last one is worth its own emphasis: **if a rule is enforced by tooling,
name the tool instead of restating the rule.** "Formatting is `prettier`; run
`pnpm format`" replaces a dozen style lines and stays correct when the config
changes.

---

## What a reviewer would send back

- A rule with no path.
- A rule with no lookup that could prove it.
- An aspiration written as if it were current practice.
- A rule the linter already enforces.
- A rule contradicted by the first file in the directory it claims to govern.
