# Baseline: a stack skill

What a good skill looks like. Mechanics are in
[../generators/skill.md](../generators/skill.md); this file is opinion, and a
team may replace it — see [README.md](README.md).

---

## The one test

**Would this skill change what an agent writes?**

If the agent would produce the same code without it, the skill is worth nothing
and costs tokens every time it triggers. Delete it and say why.

This is the test that decides everything below.

---

## The model already knows the library

It does not know **your repository's relationship with the library**. That gap
is the entire content of a good skill.

| Not this | This |
|---|---|
| "TanStack Query caches server state." | "Every query key lives in `src/queries/keys.ts`. A key written inline will be rejected in review." |
| "Use migrations to change the schema." | "Migrations are generated by `pnpm db:generate` and never hand-edited." |
| "BullMQ processes background jobs." | "Every job goes through `src/queue/worker.ts`, which sets the retry policy. Calling `new Worker()` directly bypasses it." |

The left column is documentation the model has already read. The right column is
knowledge that exists only in your repository.

**If, after reading, you have nothing for the right column, do not write the
skill.** Say so, say why, and remove the stub. A generic skill is worse than no
skill: it costs on every session and teaches nothing.

---

## Length

**Aim for 20 to 40 lines of body.** Not a rule — a signal.

Under 20 lines usually means there was not enough repository-specific knowledge
to justify the skill. Reconsider whether it should exist.

Over 40 lines usually means one of three things, and each has a fix:

| Cause | Fix |
|---|---|
| The library is being explained | Cut it. The model knows. |
| Two topics are in one skill | Split into two skills. Routing works better. |
| Rules that belong in the conventions section have drifted here | Move them. |

---

## The `description` is the most important line

It is a routing signal, not a summary. It decides whether the skill is ever
loaded, and a skill that never loads may as well not exist.

**Write the trigger — when to use it — not the contents.**

| Weak | Strong |
|---|---|
| "TanStack Query conventions" | "Use when writing or changing a data-fetching hook" |
| "Database skill" | "Use when writing a migration or changing the schema" |
| "Queue documentation" | "Use when adding a background job or changing retry behaviour" |

Test it by asking: reading only this line, would an agent know whether to open
the file? If it has to open the file to find out, the line has failed.

---

## Examples come from this repository

Real code, with its path. Never invented code presented as the house pattern.

An invented example is a lie with a long life: it becomes the pattern, and the
repository slowly grows to match a file that was never true.

Prefer the **most recently changed** file that shows the pattern. It is the best
available proxy for what the team currently believes.

If no file shows the pattern cleanly, that is itself the finding. Write a
`TODO(floor):` line asking which file should be the reference, rather than
writing an example from imagination.

---

## "What to avoid" only if it can actually happen here

A warning about a mistake this repository's setup makes impossible is noise. It
teaches the agent to spend attention on nothing.

Include a rule only if you can name the file, the pattern, or the past incident
that shows it is a live risk.

If you cannot, leave the section out entirely. An absent section costs nothing.

---

## What a reviewer would send back

- Anything that restates the library's own documentation.
- A `description` that describes contents instead of triggers.
- An example with no path, or with a path that does not exist.
- A rule you could not name a lookup for.
- Advice that would be equally true in any other repository.
