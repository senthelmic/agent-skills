# Generator: coding standards and conventions

Fills capability 3. Writes the `## Conventions` section of the instruction file
— not a separate file, because a convention an agent does not load is a
convention that does not exist.

**This is the capability most likely to fail criterion 3 (*specific*).** Be
strict about filler and lenient about length. Four true, specific rules beat
thirty generic ones.

**Read [../baselines/coding-standards.md](../baselines/coding-standards.md) first.** This file is the
mechanics; the baseline is what a good one looks like, and the team may have
replaced it. See
[../reference/baseline-resolution.md](../reference/baseline-resolution.md).

---

## Step 1 — read

A **sample** across the directories the survey identified. Not everything.

Pick, for each main directory, two or three files that are most likely to show
the pattern — the most recently changed ones are a good proxy. If you sample,
**say in the output that you sampled**.

---

## Step 2 — find the disagreements

You are looking for places where **the codebase disagrees with itself**. Those
are the questions worth asking. Where the codebase is consistent, write the
convention down; do not ask about it.

Look for disagreement in:

- **Error handling** — thrown errors versus returned result objects.
- **API response shape** — a bare object versus a wrapper such as `{ data }`.
- **Naming** — file naming, component naming, test file naming.
- **Test layout** — beside the source versus in a `tests/` tree.
- **Imports** — relative versus aliased paths.
- **Async style** — promises versus `async`/`await`.
- **What is generated** — files that must never be hand-edited.
- **Validation** — where input is validated, and with what.

---

## Step 3 — ask, at most six

Surface the disagreement with both sides and their paths:

> `src/api/orders.ts` returns a bare object; `src/api/users.ts` wraps responses
> in `{ data }`. Which is the pattern to follow?

If you find more than six disagreements, ask about the six that would most
change what an agent writes. Turn the rest into `TODO(floor):` lines.

"I don't know" is an accepted answer and becomes a `TODO(floor):` line. The
person running this may be a new joiner.

---

## Step 4 — write

```markdown
## Conventions

- <rule>. <where it applies>.
- <rule>. <where it applies>.

<TODO(floor): lines for anything unanswered, each naming the open question.>
```

**Every rule must be checkable.** If you cannot name the lookup that would prove
a rule true, it is filler — leave it out.

Reject, always:

- "Write clean, maintainable code."
- "Follow best practices."
- "Use meaningful variable names."
- "Keep functions small."
- Anything an agent already assumes without being told.

Accept:

- "Handlers in `src/api/` return `{ data }`, never a bare object."
- "Tests sit beside the source as `<name>.test.ts`."
- "`src/db/schema.ts` is generated by `pnpm db:generate` — never hand-edit it."
- "Errors cross the API boundary as `AppError`; do not throw raw `Error` there."

---

## Step 5 — re-check

Every rule you wrote, spot-check against one or two files in the directory it
claims to govern.

A rule contradicted by the code it governs is worse than no rule at all: the
agent will follow it and produce code that does not match the repository. Fix it
or turn it into a `TODO(floor):` question.

Mark anything that rests on your judgement rather than a lookup as a judgement
call when you report back to the developer.
