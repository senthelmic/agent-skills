# Plan: exhaustive backlog + the artefact builder skill

**Date:** 2026-08-08
**Continues:** `.scratch/agent-config-floor/` (phase 1, merged on `main`)
**Status:** built, on branch `artefact-builder`

> **Two deviations from this plan, made during the build.** Both are mine, not
> the user's.
>
> 1. **Cross-skill links are sibling-relative (`../agent-config-floor/…`), not
>    absolute raw-GitHub URLs.** Absolute URLs would have broken the offline
>    route — a `git clone` with no network cannot fetch them. Sibling-relative
>    paths resolve correctly in a local clone *and* over a raw-GitHub URL,
>    because raw URLs are path-based. The cost is that an agent must normalise
>    the `..` before fetching rather than sending it in the URL; both `SKILL.md`
>    files say so explicitly. It also means the symlink install route must link
>    **both** skills, which the README now states.
> 2. **No `reference/backlog.md` in the builder.** The plan gave the builder its
>    own file describing how to read and update the backlog. That would have
>    been a second description of one format. The builder links to
>    `agent-config-floor/reference/backlog-template.md` instead, which already
>    carries the merge rules.

Two changes, in order. Part A is small and lands first because Part B reads its
output. Part B is the new skill.

---

## The problem, stated plainly

Phase 1 does two things well and one thing badly.

1. It audits a repository and reports what the agents cannot do there. Good.
2. It writes stub files at the correct paths. Good.
3. It recommends further artefacts — but only inside the report, only for
   *skills*, and the report caps how much of that recommendation survives. A
   team that finishes its five stubs has no durable record of what else was
   worth building, and saved prompts and sub-agents were never recommended at
   all beyond the one floor stub each.

And once a team wants to build one of those artefacts, the only route is an
*artefact run* inside the floor skill. That run has no place for the team's own
house style, and no way to accept extra instructions at the moment of asking.

## Part A — the exhaustive backlog

### A1. A new output file: `.agent-floor/backlog.md`

The survey run gains a fourth output, beside the stubs and the report.

**The backlog lists every recommended artefact, of every type, with no cap.**
Skills, saved prompts and sub-agents all appear. The five-stub cap continues to
govern only how many stub *files* are written to disk — the anti-clutter
decision from the first trial stands, because it was about the file tree, not
about what the team is told.

Shape:

```markdown
# Agent artefact backlog

Generated by the agent config floor, <date>, floor version 1.0.0.
This file is advisory. It gates nothing and counts toward nothing.

| # | Type | Name | Proposed path | Evidence | Stub written |
|---|---|---|---|---|---|
| 1 | skill | bullmq | .claude/skills/bullmq/SKILL.md | package.json lists bullmq | yes |
| 2 | sub-agent | migration-reviewer | .claude/agents/migration-reviewer.md | 41 files under db/migrations | no — over the stub cap |
```

Rules the generating agent follows:

- **Ranked**, by which artefact would most change what an agent writes in this
  repository. Same ranking rule the stub cap already uses; now it orders the
  whole list instead of truncating it.
- **Every row carries its evidence**, in the existing style — `package.json`
  lists `bullmq`, never "you use BullMQ".
- **A row is never removed by a later survey.** Re-running merges: rows keep
  their identity by proposed path, `Stub written` and status are refreshed, new
  detections are appended. A team's own hand-added rows survive untouched.
- **The team may add rows by hand.** The backlog is theirs. An artefact they
  want that no detector would ever propose belongs here.
- **No score, no count-of-done framing.** Same rule as the report: a backlog is
  a menu, not a progress bar.

### A2. Recommend the other two types, not only skills

Step 2 of the survey currently detects a stack and recommends skills. It gains
two more recommendation passes, each cheap and each inside the existing reading
budget — no new files are read.

| Type | Recommended from |
|---|---|
| Saved prompt | repeated operations visible in CI workflows and manifest scripts — release, migrate, seed, codegen, deploy |
| Sub-agent | shape signals already gathered at depth 2 — a very large directory, a sensitive area (auth, billing, migrations), a heavy public API surface |

Both obey the existing rule: **do not invent one to fill a capability.** If
nothing in the evidence supports a recommendation, the list is short and says so.

### A3. Files that change

| File | Change |
|---|---|
| `survey-run.md` | step 2 gains the two extra recommendation passes; a new step writes the backlog |
| `reference/stubs.md` | the cap section says plainly: the cap bounds stub files, the backlog bounds nothing |
| `reference/report-template.md` | the "Stubs written" section points at `backlog.md` instead of inlining the over-cap names |
| `reference/backlog-template.md` | **new** — the exact shape, as `report-template.md` does for the report |
| `SKILL.md` | file table gains the new reference; the closing hand-off names the builder skill |

## Part B — the new skill: `agent-artefact-builder`

### B1. What it is

A sibling skill at `skills/agent-artefact-builder/`. Phase 1 audits; this builds.
It reads `.agent-floor/backlog.md`, takes one row (or a few, if the developer
asks), and writes the artefact properly.

`generators/` **moves** out of `agent-config-floor` and into this skill, along
with `artefact-run.md`, which becomes this skill's main run file. The floor skill
keeps the survey and hands off. One directory, one owner.

**Consequence to handle:** the floor skill's "resolve every link relative to
where you loaded this file" rule cannot reach a sibling skill when loaded over a
URL. The hand-off in `agent-config-floor/SKILL.md` is therefore written as an
**absolute** raw-GitHub URL to the builder's `SKILL.md`, and called out as the
one deliberate exception to the relative-link rule.

### B2. Baselines — three layers, highest wins

This is the part phase 1 has nothing of.

```
lowest   1. baselines/<type>.md            ships with this skill — the house recommendation
         2. .agent-floor/baselines/<type>.md   this repository's override
highest  3. free-form arguments at invocation
```

`<type>` is one of: `instructions`, `coding-standards`, `skill`, `code-review`,
`saved-prompt`, `sub-agent` — the same six the generators already cover.

**What each layer is.**

1. **Shipped baseline.** Opinion, not mechanics. A generator says *read the
   component directories, ask at most six questions, write this frontmatter*. A
   baseline says *what makes a good skill of this type* — how long, what a
   description must do, what to refuse to write, what a reviewer would reject.
   These are the user's own recommendations, written once, applied everywhere.
2. **Repository override.** A team drops `.agent-floor/baselines/skill.md` into
   their repo and it layers on top. The builder reads it if present, says in the
   output that it used it, and never writes to it uninvited.
3. **Invocation arguments.** Whatever the developer types when they start the
   run: `build the bullmq skill — focus on retry and backoff, we wrap the worker
   in src/queue/worker.ts`. This is merged in last and wins.

**Conflict handling.** When a layer contradicts a lower one, the higher layer
wins and the builder **says so in one line** at the end of the run — "your
repository baseline asked for examples from tests; the shipped baseline prefers
source. Used tests." Silent overriding is how a team stops trusting the tool.

**What baselines may not do.** They cannot lower the floor. A baseline cannot
turn off the claim re-check (step 5), cannot authorise an unverified assertion,
and cannot remove required frontmatter. These are rubric, not style.

### B3. Merging without re-deriving the run

The existing `artefact-run.md` shape is kept whole — scoped read, at most six
questions asked only where the code is ambiguous, write what you have even if
abandoned, then re-check every claim. The baseline layers are consulted at
exactly two points:

- **before step 2 (read)** — a baseline may widen or narrow what to read
- **before step 3 (write)** — a baseline shapes the output

Nothing else about the run changes. This keeps the two open trial questions from
phase 1 answerable: the six-question cap and the reading budget are still the
things under test.

### B4. One-at-a-time stays the default

The phase 1 rule holds: never run two artefact builds without being asked.
Thirty questions in one sitting is the failure the design exists to prevent.

A developer may explicitly ask for a batch. When they do, the builder:

- confirms the list back, with a count of the questions it expects to ask
- runs them in backlog order
- checkpoints after each one, so abandoning midway still leaves every finished
  artefact written

### B5. Files in the new skill

```
skills/agent-artefact-builder/
  SKILL.md                     what it is, how to invoke, the three baseline layers
  build-run.md                 the run (artefact-run.md, moved and extended)
  baselines/
    README.md                  what a baseline is, and what it may not do
    instructions.md
    coding-standards.md
    skill.md
    code-review.md
    saved-prompt.md
    sub-agent.md
  generators/                  moved from agent-config-floor, unchanged
  reference/
    backlog.md                 how to read and update .agent-floor/backlog.md
    baseline-resolution.md     the three layers, precedence, conflict reporting
```

`reference/paths.md` and `reference/copilot-translation.md` are needed by both
skills. They stay in `agent-config-floor` and the builder links to them by
absolute URL, same exception as B1. Duplicating them would guarantee drift.

### B6. After a build, update the backlog

The builder marks the row done, with the path it wrote and the date. This closes
the loop: the survey proposes, the builder disposes, and `backlog.md` is the one
file that shows where a team actually is.

## Open questions, for the user

1. **The six shipped baselines are opinions, and they should be yours, not
   mine.** I can draft each one from what phase 1 already implies and you edit,
   or you dictate them and I transcribe. Drafting first is faster; dictating
   first avoids me putting words in your mouth.
2. **Does the backlog get committed?** The report is the team's choice. Same for
   the backlog, or is it a working file that belongs in `.gitignore`?
3. **Naming.** `agent-artefact-builder` is descriptive but long. Alternatives:
   `agent-config-build`, `build-agent-artefact`.

## Not in scope

- Anything phase 1 deferred: stack-aware sharpening, proper Copilot translation,
  measurement and telemetry.
- npm packaging. Closed, with reasons, in the phase 1 handoff.
- Changing the six-question cap or the reading budget. Both are still under test
  in the first trial and must not move until that trial is read.
